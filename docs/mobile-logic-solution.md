# ORIGIN ERP 移动端逻辑完善方案

> 审计基线：2026-09-13 代码快照  
> 范围：`origin-erp-mobile`，并以 `origin-erp-service` 的控制器、DTO、枚举、权限种子和统一响应为契约依据  
> 目标平台：手机、PDA、H5、App/小程序；本方案不是 ESP32 方案

## 1. 结论

移动端已经具备可继续建设的外壳：登录、JWT 保存、当前用户与权限、工作台、仓库选择、库存列表/详情和统一请求层均已存在，当前 `npm run type-check` 也能通过。但现状还不能直接进入“批量补页面”阶段，因为接口路径、查询参数、权限码、ID 类型和错误语义存在契约漂移。若跳过这一层，普通角色会遇到入口消失、列表条件失效、Token 失效不退出或生产接口 404 等问题。

推荐执行顺序：

1. 先用一个契约闸门修正 API、权限、ID、状态和错误模型。
2. 再完成库存查询这一条只读闭环，形成列表/详情/扫码/刷新模板。
3. 依次落地采购入库、生产领料、成品入库、销售出库四条现场作业闭环。
4. 最后接生产订单与报工，并补齐自动化测试、弱网和多端验收。

本方案采用“一套业务规则，多端适配；读取可重试，写入不离线伪成功；页面只编排，状态机决定按钮”的原则。

## 3. 目标用户与任务边界

| 维度 | 方案 |
|---|---|
| 主要用户 | 仓管员、领料员、产线操作员、发货员 |
| 次要用户 | 主管/审批人、系统管理员 |
| 使用环境 | 单手、走动、手套/PDA、扫码频繁、网络偶发不稳定 |
| 最高频动作 | 选仓 → 扫码/查单 → 核对数量与状态 → 执行动作 → 得到可验证结果 |
| 误操作成本 | 重复入库/出库、错仓、错单、库存账实不符，属于高成本事务 |
| 主成功动作 | 对当前单据执行状态允许且自己有权限的唯一主动作 |
| 恢复动作 | 保留上下文，重新加载最新单据；冲突时禁止盲目重提 |

移动端定位为“现场执行端”，不把桌面端的复杂主数据维护和全量编辑照搬过来。首期移动端只做查询、审核/确认、上架/入库、完成/取消及必要的现场字段录入。

## 4. 目标逻辑架构

```text
Page（展示、收集意图）
  ↓
Feature Store / Composable（列表状态、详情状态、业务状态机）
  ↓
Domain Service（权限判断、动作前置条件、DTO 映射、刷新策略）
  ↓
Typed API（唯一 endpoint、query/body/response 类型）
  ↓
Request Client（Token、超时、错误分类、请求取消、日志关联）
  ↓
Spring Boot Result<T> / OpenAPI
```

建议目录：

```text
src/
├── core/
│   ├── api/                 # client、errors、endpoint contract
│   ├── auth/                # session bootstrap、permission codes
│   └── connectivity/        # online/offline 与恢复
├── shared/
│   ├── types/               # EntityId、PageResult、AsyncState
│   ├── constants/           # status metadata、storage keys
│   └── components/          # AsyncState、StatusTag、ActionFooter
└── features/
    ├── inventory/
    ├── purchase-inbound/
    ├── production-picking/
    ├── finished-warehousing/
    ├── sales-outbound/
    └── production-order/
```

每个 feature 只包含 `api.ts`、`types.ts`、`store.ts/composable.ts`、`pages/`；页面不得直接写状态流转规则。现有 `src/apps/inventory` 可以迁入 `features/inventory`，也可暂时保留路径、只把内部依赖改到新分层，避免一次性大重构。

### 4.1 核心数据类型

枚举契约统一如下：

- 前后端枚举字段只交换稳定的 `code`，当前后端为数字 code。
- 中文名称只存在于各端展示映射中，不把 label、枚举名称或 ordinal 发送到接口。
- 移动端筛选、状态机判断和写操作参数统一引用 `src/constants/domain-enums.ts`，禁止散落魔法数字。
- 后端响应通过 `@JsonValue` 输出 code；兼容旧输入不代表新客户端可以继续发送旧格式。

```ts
type EntityId = string;
type DecimalValue = string | number; // 只用于接收过渡；提交前统一转十进制字符串
type AsyncStatus = "idle" | "loading" | "ready" | "empty" | "error" | "offline";

interface AppError {
  kind: "network" | "timeout" | "unauthorized" | "forbidden" |
        "validation" | "conflict" | "server" | "contract";
  message: string;
  code?: number;
  statusCode?: number;
  retryable: boolean;
  requestId?: string;
}
```

状态码和状态文案不能散落在页面中。每个领域建立 `code → label/tone/allowedActions` 映射，后端枚举为唯一来源。例如采购入库 `0 草稿 → 1 已审核 → 2 已上架`；销售出库是 `0 草稿 → 1 已确认 → 3 已完成`，取消为 `2`，不能假定状态编码连续。

后端 `BigDecimal` 当前以 JSON 数字返回。移动端首期可以用 `number | string` 接收，但数量和金额不得在页面用浮点数做权威计算；提交前规范化为十进制字符串，最终建议后端也以字符串输出精确数值。

### 4.2 请求与会话规则

- GET 查询直接序列化扁平 query；数组、日期和空值行为写单测。
- 读取请求可由用户重试；写请求不自动重试，不允许离线排队后提示“成功”。
- 页面切换、重复搜索时取消或忽略旧请求，使用递增请求序号避免慢响应覆盖新结果。
- `401`：清 Token、清用户/仓库上下文、记录 return URL、重新登录后回到安全页面。
- `403`：保留登录态，显示“无此操作权限”，并重新拉取权限；不得当作掉线。
- `409` 或业务冲突：提示“单据状态已变化”，拉取详情并重新计算可用动作。
- 校验错误保留全部输入，并把字段错误落到具体控件，不只 Toast。
- 当前仓库只持久化 `warehouseId`；恢复时重新从可用仓库列表校验，避免保存整个过期对象。
- 仓库切换是全局业务事件：立即使依赖旧仓库的缓存失效，并刷新工作台摘要和当前业务列表。
- 后端应为无效/过期 JWT 输出统一 401 JSON，并为事务写接口逐步增加幂等键或版本号。客户端在此之前至少采用动作锁和提交后刷新。
- 原生端 `VITE_NATIVE_API_BASE_URL` 为空时应在启动期明确阻断并给出配置错误，不能继续以相对地址发请求。

| M4 | 生产报工 | 报工列表/详情/新增 | 提交、审核、驳回、完成 | `/prd/report` | 明确移动端角色和报工字段 |

### 5.1 通用单据状态机

```text
列表 → 详情 → 读取最新状态 → 计算 allowedActions
                         ↓
              二次核对 / 填写现场字段
                         ↓
                 提交中（动作锁）
                 ↙               ↘
       成功：刷新详情/摘要      失败：保留上下文
                               ├─ 无权限：解释并返回
                               ├─ 状态冲突：刷新单据
                               └─ 网络失败：明确未确认成功，允许查证后重试
```

任何会改变库存或单据状态的按钮，都必须同时满足：`有动作权限`、`后端状态允许`、`必填现场数据完整`、`当前无提交`。UI 隐藏无权限动作；状态不允许但用户可能疑惑时，保留禁用按钮并说明原因。

### 5.2 必须显式告知用户的连锁副作用

- 销售订单确认会逐行预占库存；库存不足时后端整体回滚。
- 销售出库“完成”才真正扣减在库与预占，并写库存流水。
- 生产订单“下达”会计算 BOM 净需求，并自动生成采购需求、草稿采购订单和生产领料单。
- 全部领料完成后，生产订单才具备开工条件。
- 报工完成会累计生产订单完成量，并通过后端事件自动生成成品入库单。
- 采购入库“上架”会更新库存，并影响等待物料的生产领料流程。

因此确认面板不能只写“确定操作吗”，而应说明将发生的库存或下游单据变化；动作成功页应显示新状态和受影响对象，便于现场核对。

## 6. 页面状态模型

| 状态 | 用户看到 | 主动作 | 恢复 |
|---|---|---|---|
| 首次加载 | 与真实布局一致的骨架屏 | 无 | 等待请求 |
| 就绪 | 列表/详情、当前仓库、状态标签 | 当前唯一主动作 | 正常操作 |
| 空数据 | 空态原因与当前筛选 | “清除筛选”或“重新扫码” | 不进入死路 |
| 分页加载 | 保留已有记录，底部小型进度 | 无 | 失败只影响下一页 |
| 局部失败 | 已成功区域继续展示，失败卡片单独标识 | “重试此项” | 不把失败显示成 0/暂无 |
| 离线 | 顶部持续离线条；只读缓存标明时间 | “检测网络” | 禁止库存写操作 |
| 无权限 | 所需权限与联系管理员说明 | “返回工作台” | 可刷新权限 |
| 提交中 | 主按钮锁定，文案改为“正在确认…” | 无重复提交 | 不允许返回造成误解 |
| 状态冲突 | 最新状态、原操作为何失效 | “刷新单据” | 重新计算动作 |
| 成功 | 明确动作、单号、时间和新状态 | “继续下一单” | 同步刷新详情、列表和摘要 |

## 7. 信息层级与交互契约

详情页固定遵循：标题/单号 → 当前状态 → 物料/客户/订单关键信息 → 数量与仓库 → 补充字段 → 主动作。P0 信息和主动作在紧凑屏上应可快速到达，动作区在小屏使用安全区感知的底部固定栏。

### 交互 1：选择仓库

- 触发：点击工作台或筛选区“当前仓库”。
- 前置：已加载可访问仓库；只有一个仓库时直接使用并说明。
- 成功：只保存 ID，刷新所有依赖仓库的列表与摘要，播报“已切换到 ×× 仓库”。
- 失败：保持原仓库；不得让页面进入“显示新仓、数据仍是旧仓”的混合态。
- 事件：`warehouse_changed`。

### 交互 2：扫码分派

- 触发：扫一扫或业务页扫码按钮。
- 系统响应：解析条码类型；在当前业务域优先查询，不在当前域时给出“库存查询/查找单据/重扫”的明确选择。
- 失败：区分取消、相机权限拒绝、无匹配、网络失败；允许手输。
- 不得：把任意扫码结果直接当业务 ID 发起写操作。
- 事件：`scan_completed`、`scan_unmatched`。

### 交互 3：执行库存事务动作

- 触发：审核、确认领料、上架、入库、完成出库等。
- 前置：权限、最新状态、仓库和必填项全部满足。
- 系统响应：按钮动作锁；高风险动作展示单号、物料/行数、数量、仓库的核对页或确认表。
- 成功：展示新状态并刷新详情、来源列表、工作台摘要。
- 失败：保留表单；网络不确定时文案为“未确认是否成功，请先刷新单据”，避免盲目重提。
- 事件：`document_action_started/succeeded/failed`，附 `documentType/action`，不记录敏感业务内容。

### 交互 4：会话失效

- 触发：统一 401。
- 系统响应：只执行一次全局退出；保存安全 return URL。
- 成功：重新登录后回到原只读页面；未完成的写操作不自动恢复提交。
- 无权限 403 不得走本流程。
- 事件：`session_expired`。

## 9. 响应式、视觉与可访问性

- 320–374：减少非任务装饰；主动作固定到底部安全区；筛选使用抽屉/底部面板。
- 375–430：默认手机布局；卡片单列，工作台摘要可双列。
- 431–480：内容最大宽度受控，不拉长单行字段。
- 600–839 PDA/平板：列表 + 详情双栏；动作栏固定在详情栏，不扩展为整屏宽按钮。
- 横屏低高度：顶部信息压缩，正文滚动，动作始终不被键盘遮挡。
- 复用 `uni.scss` 现有 `$app-color-*`、`$app-radius-control`、`$app-control-height`、`$app-page-gutter`；页面中的硬编码逐步替换为令牌。
- 状态不可只靠颜色：标签必须同时显示文字；装饰图标对读屏隐藏。
- H5 指针目标至少符合 WCAG 2.2 的 24×24 CSS px 或有效间距；现场主操作建议不低于 44 CSS px，Android/PDA 采用不低于 48dp 的命中区。
- 文字缩放后不得裁切状态、数量、错误和主动作；弹层打开后焦点进入标题，关闭后回到触发控件。
- 动画只解释状态变化，150–250ms；骨架不得伪装真实进度；系统减少动态效果时关闭非必要过渡。

需要新增或统一的组件：`AsyncStateView`、`OfflineBanner`、`WarehouseContextBar`、`StatusTag`、`DocumentCard`、`ActionFooter`、`ConfirmActionSheet`、`QuantityField`。这些组件应服务至少两个业务域，否则先保留为 feature 内组件。

## 10. Sol–Luna 集群执行方式

采用一个 Sol 负责高风险契约与集成审查、两个 Luna 负责边界清楚的功能包；根任务负责排期、冲突管理和验收。共享文件不能并行改，必须在每波开始前锁定负责人。

| 波次 | Sol 轨 | Luna A 轨 | Luna B 轨 | 合流闸门 |
|---|---|---|---|---|
| Wave 0 | 冻结 OpenAPI、权限、ID、状态和错误契约 | 建请求层/状态机测试夹具 | 建页面状态与 E2E 场景清单 | 契约表通过后才能写业务页 |
| Wave 1 | 改 `core/api`、会话、权限常量并审查 | 完成库存闭环 | 完成通用列表/详情组件 | 类型检查 + 契约测试 + 库存 E2E |
| Wave 2 | 审查事务状态机和并发风险 | 采购入库 + 成品入库 | 生产领料 | 每个动作有权限/状态/失败用例 |
| Wave 3 | 审查库存扣减和冲突恢复 | 销售出库 | 生产订单 + 报工（若契约已定） | 真后端集成 + 现场设备验收 |
| Wave 4 | 发布审查 | 多端回归与可访问性 | 弱网、扫码、性能回归 | 发布清单全部通过 |

工作约束：

- Sol 独占 `src/core/**`、`src/shared/types/**`、权限常量和契约文档。
- Luna 功能轨只改分配的 `src/features/<feature>/**`；`pages.json`、全局样式和共享组件由根任务串行合并。
- 每个任务都带“允许修改路径、接口契约、状态矩阵、验收命令、不得更改项”。
- 每波结束先集成再开下一波，禁止多个 agent 同时修同一共享文件。
- 每个功能提交都必须附：接口样例、权限矩阵、状态转换、三类失败截图和执行过的命令。
- 页面增多后将低频业务放入 `subPackages`，主包保留登录、工作台和我的；是否分包在 Wave 1 结束时用包体数据决定。

## 11. 测试与验收

### 自动化分层

1. 单元测试：query 序列化、Long 字符串、错误分类、权限判断、状态 `allowedActions`、旧请求覆盖保护。
2. API 契约测试：从 `/v3/api-docs` 固化路径/方法/schema；校验前端 endpoint 和权限矩阵，至少覆盖所有移动端调用。
3. Store/组件测试：首次加载、空、分页失败、局部失败、403、冲突、提交锁和成功刷新。
4. E2E：登录恢复、切仓、扫码无匹配、库存查询、采购上架、领料确认、成品入库、销售完成出库、Token 过期。
5. 真机：Android PDA 优先；再验 H5、App、微信小程序的域名、相机权限、系统返回键、安全区和键盘。

### 每个业务的 Definition of Done

- 接口路径、方法、query/body、响应和状态码与 OpenAPI 一致。
- 普通角色只看到可访问入口，详情动作按独立权限控制。
- loading/empty/error/offline/forbidden/conflict/success 均有可恢复界面。
- 写操作不可重复提交，失败不丢输入，不产生“假成功”。
- 切仓、返回页面和成功动作后数据刷新范围正确。
- 320–374、375–430、431–480、600–839 四档无关键内容裁切。
- `npm run type-check`、单元测试、H5 构建、目标端构建和关键 E2E 全部通过。

## 12. 里程碑与风险控制

| 里程碑 | 产出 | 退出条件 |
|---|---|---|
| M0 契约闸门 | OpenAPI 快照、endpoint/permission/status 常量、ID 与错误模型 | P0 漂移清零，普通测试角色可访问 |
| M1 只读闭环 | 库存搜索、扫码定位、详情、分页、弱网恢复 | 可作为其他列表/详情模板 |
| M2 仓储生产闭环 | 采购入库、生产领料、成品入库 | 三条库存事务具备防重与冲突恢复 |
| M3 销售/生产闭环 | 销售出库、生产订单，按确认后的范围接报工 | 工作台入口不再指向占位页 |
| M4 发布 | 自动化、PDA/多端验收、监控与发布回滚清单 | 阻断级缺陷为零 |

主要风险与对策：

- **后端“基本就绪”但契约仍漂移**：M0 以 OpenAPI + 控制器事实为准，先锁路径和状态，不靠 README 推断。
- **事务重复提交**：客户端动作锁只能降低概率；最终应由后端提供幂等或乐观锁，并在冲突时返回可识别状态。
- **权限种子缺失**：先补权限数据与角色矩阵，再做 UI 显隐，否则管理员测试会掩盖问题。
- **弱网下结果不确定**：不自动重试写入；先查单据最新状态，再允许人工重试。
- **多端 API 差异**：`uni.request` 的方法支持和小程序域名白名单按目标平台验收，不能只用 H5 通过代表全部通过。
- **发布面过宽**：先明确首发平台，移除未使用依赖与非目标平台脚本；`dist/`、`output/`、`.idea/` 不作为源码资产管理。

## 13. 需确认的产品决策（实施审批闸门）

在进入 Wave 1 业务实现前，应由产品/业务确认以下三点：

1. 首个上线闭环是否按“库存 → 采购入库 → 生产领料 → 成品入库 → 销售出库”排序。
2. 生产领料是否要求后端补详情接口；若不补，列表返回必须包含现场核对所需全部字段。
3. 扫码编码规则：物料码、单据码、批次码是否有可判别前缀，以及无法判别时的默认落点。

本任务属于多流程和库存事务的高复杂度设计，方案批准后再进入实现，避免在权限、状态与扫码规则未定时生成返工页面。
